# 🔴 КРИТИЧНА ЗАДАЧА: медіа-файли стираються після кожного апдейта

## Проблема

У git-історії видно повторюваний патерн:

```
Add files via upload           ← студент заливає відео
Delete public/videos/case1.mp4 ← через якийсь час воно стирається
Add files via upload           ← студент заливає знову
Delete public/videos/case2.mp4 ← знову стирається
...
```

У `.gitignore` вже є маркер цієї проблеми:
```
# Heavy Media - Protect from sync deletion
public/videos/*
!public/videos/.gitkeep
```

Тобто раніше хтось намагався це обійти, але поточна схема (ігнорувати
відео в git) лише погіршує ситуацію — git не відстежує файли, тому
будь-який sync їх зносить без варіантів відновити.

## Причина

Студент працює через **Gemini / Google AI Studio**. AI Studio працює
"шаблонами": коли користувач просить щось оновити, воно **регенерує
проект цілком** зі свого "бачення" і пушить у репозиторій. Файли,
яких немає у промпті AI (як завантажені студентом відео), зникають.

Додатково, файли з `public/videos/*` у gitignore → їх **немає в git
взагалі** → після регенерації їх **неможливо відновити**.

## Що саме треба захистити

1. 🎥 Відео кейсів у `public/videos/` — 4 шт. (зараз є 3, case4 відсутній)
2. 🖼️ Картинки, які студент завантажить у `public/` (логотип, фото,
   заставки)
3. 📝 У майбутньому — заявки з форми (зараз `handleSubmit` просто
   робить `console.log`, нічого не зберігається і не відправляється)

## Варіанти розв'язання (обговорити завтра)

### Варіант 1 — Винести відео на зовнішній хостинг ⭐ РЕКОМЕНДУЮ

Відео завантажуються на CDN, у коді лишається тільки URL. Жоден
sync не зможе їх торкнутись.

Безкоштовні варіанти:
- **Cloudinary** (25 ГБ storage + 25 ГБ трафіку/міс безкоштовно)
  - Завантажуєш через веб-інтерфейс
  - Отримуєш URL типу `https://res.cloudinary.com/.../case1.mp4`
  - Вставляєш у `MEDIA.case1Video`
- **Bunny.net Stream** — ~$1/міс за мінімум, дуже дешево
- **YouTube (unlisted)** — безкоштовно, але треба iframe замість
  `<video>`, трохи переробити код

Плюси: медіа не може бути стерто кодом взагалі; швидка CDN-доставка;
репозиторій не роздувається.
Мінуси: залежність від зовнішнього сервісу (якщо акаунт заблокують —
відео зникнуть).

### Варіант 2 — Закомітити відео в git і прибрати з .gitignore

Прибираємо рядки `public/videos/*` з `.gitignore`. Відео стають
частиною git. При будь-якому sync вони відновлюються з history.

Плюси: все у одному місці; просто; безкоштовно.
Мінуси: git-репо роздувається; GitHub не любить файли >100 МБ; після
кількох ітерацій репо буде важким.

Підходить якщо: сумарний розмір усіх відео < 50 МБ.

### Варіант 3 — Git LFS

Правильне технічне рішення для великих бінарників у git. Файли
зберігаються окремо, git тримає лише посилання.

Плюси: індустріальний стандарт.
Мінуси: студенту треба встановити Git LFS на комп; GitHub дає лише
1 ГБ LFS безкоштовно; додаткова складність у поясненні.

Для чайника — **забагато**.

### Варіант 4 — Змінити інструмент розробки

Замість Gemini, який регенерує проект цілком, перейти на:
- **Claude Code** (я) — працює інкрементально через git, нічого не
  стирає
- **ChatGPT Codex** — те саме
- **Cursor** — локальний редактор, студент бачить що міняється

Це НЕ розв'язує проблему для тих відео, що вже стерлись, але
запобігає повторенню.

### Варіант 5 — Захисний промпт для Gemini

Додати до всіх промптів студенту:
> "НЕ видаляй файли з public/ і public/videos/. НЕ змінюй .gitignore.
>  Торкайся ТІЛЬКИ src/ папки."

Плюси: дешево і швидко.
Мінуси: Gemini часто ігнорує такі інструкції при регенерації.
Ненадійно.

## Рекомендований план на завтра

**Комбінація варіантів 1 + 4:**

1. **Для відео** → Cloudinary (безкоштовний акаунт).
   - Створити акаунт https://cloudinary.com
   - Залити 3 існуючі `case1-3.mp4` туди
   - У `Home.tsx` у блоці `MEDIA` замінити `case1Video` etc. на
     Cloudinary-URL
   - Для case4 — коли студент запише/надішле відео, теж залити
     туди, а не в репозиторій

2. **Для картинок** (які менші) → закомітити в git
   - Прибрати `public/videos/*` з `.gitignore` (якщо не використовуємо
     Cloudinary)
   - Або лишити, якщо все на CDN
   - Картинки <500 КБ спокійно живуть у git

3. **Зафіксувати workflow** — написати студенту коротку інструкцію:
   - "Для нових відео — заливай на Cloudinary, не в репо"
   - "Для нових картинок — заливай у `public/` через GitHub"
   - "Не використовуй Gemini для доробок — тільки Claude Code або Codex"

## Що НЕ робити

- ❌ Не робити `git push --force` — це затре історію і медіа з неї
- ❌ Не видаляти `.gitignore` повністю — там ще `node_modules` і
  `.env`, вони мають лишатись проігнорованими
- ❌ Не заливати `.env` у репо (паролі/ключі)
